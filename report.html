01. Project Overview

The system is an innovative medical document management solution utilizing blockchain and IPFS technologies to ensure security, confidentiality, and traceability of medical records. It operates on a decentralized architecture where large document payloads are stored off-chain on IPFS, while cryptographic hashes, patient consent, and access revocation states are anchored on Ethereum or Polygon. This hybrid approach minimizes gas costs while establishing a tamper-evident, provenance-aware lineage for every medical record created, updated, or revoked.

Contract Breakdown

IdentityRegistry.sol: Centralized role registry replacing repeated per-contract storage. Manages roles for Admin, Doctor, and Patient.

ConsentLedger.sol: Explicit consent ledger managing access scope, grant time, expiry time, and revocation status for fine-grained authorization.

RecordRegistry.sol: Provenance-aware record store using bytes32 document and metadata hashes, linking updates to parent records via rootId and parentId.

03. Architecture Deep Dive

End-to-End Document Upload Flow

1
Consent Verification: Doctor initiates upload. Smart contract checks ConsentLedger to ensure the patient has granted an active, unexpired upload scope.
2
IPFS Anchoring: The raw medical document and JSON metadata are uploaded to the local IPFS Kubo node.
3
Hash Generation: IPFS returns unique Content Identifiers (CIDs) which are hashed into bytes32 for compact on-chain storage.
4
State Commit: Doctor calls createRecord on RecordRegistry.sol, committing the document hashes. The contract emits a RecordCreated event.

Access Control Lifecycle

1
Grant: Patient signs a transaction setting a consent scope and expiry for a specific Doctor address in ConsentLedger.
2
Read: Doctor attempts to read. Contract evaluates block.timestamp < consent.expiry and valid scope.
3
Revoke: Patient explicitly revokes access. The ledger state is updated to reflect revoked status, immediately halting Doctor read/write capabilities.

05. Improvements Made & Proposed

A) Already Implemented

Moved from generic string-based metadata storage to bytes32 hashes. Extracted repeated access checks into a centralized IdentityRegistry.sol. Implemented explicit ConsentLedger.sol replacing boolean flags.

B) Proposed Improvements

1. Remove recordId From Record Storage

Why: The mapping already keys by recordId. Storing it again inside the struct wastes a full storage slot.

Effort: 2 Hours | Impact: Performance | Priority: P1

2. Replace Write-Heavy Arrays With Event-First Indexing

Why: Pushing to childVersions arrays on-chain is expensive. We should reconstruct lineage off-chain via emitted RecordVersioned events.

Effort: 2 Days | Impact: Performance | Priority: P1

3. Make Consent Validation Read-Only On Hot Path

Why: Evaluating consent currently triggers state-cleanup if expired, increasing read-path gas unpredictably.

Effort: 4 Hours | Impact: Security | Priority: P2

06. Gas Cost & Performance Analysis

Key Insight: At 200 gwei congestion, costs are 10× higher than baseline. Shifting document identifiers to bytes32 and leveraging Polygon L2 reduces write costs by ~99.7% compared to Ethereum Mainnet storage of raw strings.

07. Research Contribution Summary

1. Gas-Optimized State Design

Solves: Medical records systems traditionally bloat on-chain state with strings and arrays.
Status: Partially Implemented. bytes32 hashes live. Needs event-centric array removal.
Paper Readiness: Require benchmarking numeric IDs vs hash IDs.

2. Enforceable Consent Ledger

Solves: Boolean access flags lack healthcare realism (expiry, scope).
Status: Fully Implemented in smart contracts.
Paper Readiness: Complete. Requires frontend integration showcase.

3. Provenance-Aware Verification

Solves: Overwriting records destroys history; naive arrays cost too much gas.
Status: Implemented via parentId and rootId structures.
Paper Readiness: Needs Web UI timeline view to visualize the event lineage.
